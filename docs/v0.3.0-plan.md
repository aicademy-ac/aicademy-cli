# Aicademy CLI v0.3.0 Plan — Textual TUI + GitHub CLI-style auth

> Generated from the design session for `aicademy-cli`.
> Goal: make the CLI the best-performing, most ergonomic Kubernetes exam practice tool.

---

## 1. Goals

- Keep the existing fast, scriptable CLI commands unchanged for power users.
- Add a full-screen Textual TUI under `aicademy tui` for guided practice.
- Adopt a GitHub CLI-style OAuth + CLI token flow so users never have to copy-paste secrets manually.
- Normalize commands under clear subcommands (`auth`, `question`, `tools`) while keeping friendly top-level shortcuts.
- Make the TUI performant: non-blocking API calls, async state, and shell integration that lets users run `kubectl`, `vim`, and copy-paste commands without leaving the TUI.

---

## 3. Authentication flow (GitHub CLI-like)

1. `aicademy auth login` (or `aicademy login`) opens the default browser to `https://www.aicademy.ac/auth?cli=1`.
2. The web app performs OAuth and shows a short-lived device code.
3. The CLI polls `POST /api/cli-token` with the device code.
4. Server returns a CLI token bound to the user.
5. CLI stores the token in `~/.aicademy/config.json`.

Existing long-lived CLI tokens are still supported as a fallback.

API changes needed in `www.aicademy.ac`:

- `GET /api/auth/cli-code?device_code=...` — polling endpoint for CLI login status.
- `POST /api/auth/cli-token` — exchange device code for a CLI token.
- Update `src/routes/(marketing)/auth/+page.server.ts` to generate and display the device code when `cli=1`.

## 5. Shell integration (split-terminal workflow)

The user wants to run `kubectl`, `vim`, and copy-paste commands while the TUI stays visible. The chosen approach is **Option B: split-terminal / tmux-style session** rather than embedding a full terminal inside Textual.

### Linux / macOS

Use **tmux** as the orchestrator:

- When the user presses `k` (kubectl shell) or opens a shell from the TUI, the CLI launches a new tmux pane/window split below the TUI.
- The TUI stays in the top pane, the shell runs in the bottom pane.
- The shell is pre-configured with the active `KUBECONFIG` pointing to the running KIND cluster.
- The user can run `kubectl`, `vim`, `curl`, etc. normally.
- When they finish, they close the pane and return focus to the TUI.

Requirements: `tmux` installed. If missing, the TUI prompts the user to install it.

### Windows

Use **Windows Terminal** or **ConEmu** split-pane support if available; otherwise fall back to launching a new `cmd.exe` / `pwsh.exe` window with `KUBECONFIG` set.

Preferred Windows path:

1. Detect Windows Terminal via `WT_SESSION` environment variable.
2. If Windows Terminal is available, launch a new pane with `wt -p "Aicademy Shell" -d .` or use `wt split-pane` if supported.
3. If not available, fall back to `start cmd /k` with the environment configured.

### tmux command example (Linux/macOS)

```bash
tmux split-window -v -l 30% "KUBECONFIG=~/.aicademy/kubeconfig-aicademy-session bash"
```

The TUI app itself can also be started inside a tmux session named `aicademy` so the user can always detach and reattach:

```bash
tmux new-session -s aicademy -n tui aicademy tui
```

### Shell helpers

- On session start, write a temporary `KUBECONFIG` to `~/.aicademy/kubeconfig-aicademy-session`.
- Export a `kubectl` alias that uses this config automatically in the spawned shell.
- Provide a `hint` command in the shell that prints the current question's tasks.

## 6. API changes needed in `www.aicademy.ac`

- `GET /api/auth/cli-code?device_code=...` — return `pending`, `authorized`, or `expired`.
- `POST /api/auth/cli-token` — accept `device_code`, return `{ token: string }`.
- `GET /api/auth/me` — return `{ id, email, name, role, subscriptionStatus, labsUntil, xp }` for `whoami`.
- Existing endpoints remain unchanged:
  - `POST /api/practice/sessions`
  - `GET /api/practice/sessions`
  - `POST /api/practice/sessions/{id}`
  - `PATCH /api/practice/sessions/{id}`
  - `GET /api/practice/questions/{category}/{id}`

---

## 7. Performance design

- All API calls use `httpx.AsyncClient` with connection pooling and reasonable timeouts.
- TUI state is reactive via Textual's reactive attributes; no blocking I/O on the main thread.
- `kubectl` / `kind` / shell commands are spawned via `asyncio.create_subprocess_exec` or tmux so the TUI remains responsive.
- Question list and user progress are cached in memory; refresh in the background when the TUI regains focus.
- Verify checks run in a subprocess and stream output to the TUI.

## 10. Migration and deprecation

- `aicademy install-tool` still works but prints a deprecation warning pointing to `aicademy tools --install`.
- `aicademy verify` remains a shortcut to `aicademy question verify` indefinitely.
- `aicademy question start` remains the canonical command; `aicademy launch` and `aicademy start` are aliases.
- `aicademy auth` subcommands are new; `aicademy login`/`logout`/`whoami` are top-level aliases.
- No breaking changes to existing `aicademy question start/verify/clear` behavior or session storage.

## 13. Context from this session

- The `www.aicademy.ac` app has been hardened through the `docs/detailed-action-plan.md` work.
- Payment enrollment is centralized in `src/lib/server/enrollment.ts`.
- Labs access is centralized in `src/lib/server/practice.ts` and `src/lib/server/labs-access.ts`.
- Practice session verification now uses a signed `verificationToken` and detailed `checkResults` for declarative questions; legacy bash questions still rely on client-reported `passed`.
- Public API endpoints now have long-lived `Cache-Control` headers.
- Account deletion and admin deletion are implemented and cascade through all user-related tables.
- A `security.txt` file is served at `https://aicademy.ac/.well-known/security.txt`.
- The CLI should target `https://www.aicademy.ac/api` and expect these API contracts:
  - `POST /api/practice/sessions` returns `{ sessionId, question, verificationToken, ... }`.
  - `POST /api/practice/sessions/{id}` accepts `{ passed, message, score, verificationToken, checkResults }`.
  - `GET /api/practice/questions/{category}/{id}` requires an active session and returns full question details including `verifyChecks`.

## 14. Notes for implementers

- Keep the existing `config.set_active_session` shape; add `verificationToken` to it.
- Ensure the TUI can be run without tmux installed; in that case, disable the shell split feature and show a helpful message.
- Use absolute paths for `KUBECONFIG` and temporary files to avoid issues when the shell changes directories.
- Avoid storing PII in logs; use the same redaction approach as the web app.
- Keep the CLI Python 3.9 compatible to match `pyproject.toml`.
